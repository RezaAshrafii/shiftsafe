# فاز ۴ — اجرای end-to-end baseline

## چرا این فاز لازم بود؟

تا قبل از این فاز، گیت کیفیت، split، baseline و metric هرکدام جداگانه وجود داشتند. این برای تست واحد خوب است، اما برای ارائه‌ی MVP کافی نیست. حالا یک تابع واحد داریم که جریان آزمایش را از داده‌ی خام تا نتیجه‌ی قابل ذخیره اجرا می‌کند.

## مسیر اجرای جدید

```text
DataFrame
  ↓
بررسی target
  ↓
split زمانی یا گروهی
  ↓
baseline آموزش
  ↓
پیش‌بینی روی test
  ↓
محاسبه metric
  ↓
خروجی JSON-friendly
```

تابع اصلی:

```python
run_baseline_evaluation(
    frame,
    target_column,
    task,
    split_strategy,
    split_column=...,
)
```

## دو حالت فعلی

### رگرسیون زمانی

داده ابتدا با زمان جدا می‌شود. میانگین target در train به‌عنوان baseline محاسبه می‌شود و روی test قرار می‌گیرد. سپس MAE و RMSE گزارش می‌شوند.

### طبقه‌بندی گروهی

گروه‌های کامل جدا می‌شوند. پرتکرارترین کلاس train برای test پیش‌بینی می‌شود و accuracy و balanced accuracy گزارش می‌شوند.

## شکل خروجی

خروجی شامل این موارد است:

- نوع مسئله؛
- روش split؛
- ستون split؛
- ستون target؛
- تعداد ردیف‌های train و test؛
- نام baseline؛
- metricها.

این خروجی مستقیماً قابلیت تبدیل به JSON یا گزارش Markdown را دارد.

## خطاهای مهم

اگر target وجود نداشته باشد یا مقدار خالی داشته باشد، قبل از split اجرای pipeline متوقف می‌شود. اگر task یا split ناشناخته باشد، خطای deterministic برمی‌گردد.

## چه چیزی هنوز ساخته نشده است؟

این pipeline هنوز مدل یادگیری ماشین، prediction interval، conformal calibration، drift test یا تصمیم تجاری ندارد. عمدی است: اکنون یک مسیر سالم و قابل مشاهده داریم تا مدل آینده با baseline مقایسه شود.

## توضیح شفاهی آماده

«در فاز چهار، اجزای قبلی را در یک جریان end-to-end وصل کردم. داده ابتدا بررسی می‌شود، سپس با split زمانی یا گروهی بدون leakage جدا می‌شود، baseline فقط روی train ساخته می‌شود، روی test پیش‌بینی می‌کند و metric نهایی برمی‌گردد. بنابراین از اینجا به بعد هر مدل جدید باید در همین مسیر اجرا شود و نسبت به baseline عدد قابل مقایسه بدهد.»
