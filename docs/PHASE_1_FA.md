# فاز ۱ ShiftSafe: قرارداد ورودی و اعتبارسنجی داده

## این فاز چه مشکلی را حل می‌کند؟

قبل از اینکه مدل machine learning بسازیم، باید بدانیم داده‌ای که به سیستم داده شده اصلاً قابل بررسی هست یا نه.

اگر ستون target وجود نداشته باشد، اگر فایل خالی باشد یا اگر زمان داده وجود نداشته باشد، ساختن مدل بی‌معنی است. این فاز جلوی همین اشتباه را می‌گیرد.

## قرارداد داده چیست؟

فایل `contracts.py` یک مدل به نام `DataContract` دارد. این مدل به ShiftSafe می‌گوید:

- اسم ستون هدف چیست؛
- اسم ستون زمان چیست؛
- آیا ستون شناسه داریم؛
- آیا ستون گروه یا سایت داریم؛
- اگر classification باشد، label مثبت چیست.

مثال:

```python
DataContract(
    target="failure",
    time_column="timestamp",
    group_columns=["site"],
)
```

یعنی ستون `failure` چیزی است که می‌خواهیم پیش‌بینی کنیم، `timestamp` زمان مشاهده است و `site` برای جلوگیری از قاطی‌شدن سایت‌ها بین train و test مهم است.

## تابع اصلی چه می‌کند؟

تابع `run_quality_gate` در `checks.py` یک DataFrame و یک DataContract می‌گیرد.

بعد این مراحل را انجام می‌دهد:

1. ستون‌های لازم را جمع می‌کند؛
2. بررسی می‌کند dataset خالی نباشد؛
3. بررسی می‌کند target وجود داشته باشد؛
4. اگر زمان تعریف شده، بررسی می‌کند time column وجود داشته باشد؛
5. missing cells را می‌شمارد؛
6. duplicate rows را می‌شمارد؛
7. بررسی می‌کند target مقدار خالی نداشته باشد؛
8. زمان را parse می‌کند؛
9. مرتب‌بودن زمانی را بررسی می‌کند؛
10. نتیجه را به شکل summary برمی‌گرداند.

## معنی تصمیم‌ها

### `STOP`

یعنی یک مشکل بنیادی داریم و اجرای مدل در این مرحله نباید ادامه پیدا کند.

نمونه‌ها:

- فایل خالی است؛
- target وجود ندارد؛
- time column لازم وجود ندارد؛
- target خالی دارد؛
- ستون group لازم وجود ندارد.

### `REWORK`

یعنی داده کاملاً نابود نیست، اما قبل از مدل‌سازی باید اصلاح یا بررسی شود.

نمونه‌ها:

- duplicate rows؛
- timestamp قابل parse نیست؛
- زمان مرتب نیست.

### `CONTINUE`

یعنی فقط این دروازهٔ اولیه را رد کرده‌ایم. این تصمیم به معنی خوب‌بودن مدل، سوددهی، ایمنی یا آمادگی production نیست.

## چرا خطاها اسم مشخص دارند؟

به‌جای اینکه فقط بنویسیم «داده خراب است»، خروجی دلیل ماشین‌خوان دارد:

```json
{
  "status": "STOP",
  "reasons": ["target_column_missing"]
}
```

این کار دو فایده دارد:

- کاربر انسانی می‌فهمد چه چیزی را باید اصلاح کند؛
- در آینده API، dashboard یا pipeline می‌تواند بر اساس همین reason تصمیم بگیرد.

## تست‌هایی که اضافه شد

در `tests/test_quality_gate.py` اکنون این حالت‌ها تست می‌شوند:

- dataset سالم؛
- target خالی؛
- زمان غیرمرتب؛
- dataset خالی؛
- target ناموجود؛
- time column ناموجود؛
- group column ناموجود.

هر test یک رفتار قابل انتظار را تثبیت می‌کند. یعنی اگر در آینده کسی کد را تغییر دهد و این رفتار خراب شود، CI باید فوراً آن را نشان دهد.

## چیزهایی که هنوز این فاز انجام نمی‌دهد

این فاز هنوز این موارد را انجام نمی‌دهد:

- train/test split واقعی؛
- ساخت model؛
- تشخیص leakage بین train و test؛
- calibration؛
- uncertainty؛
- distribution shift؛
- prediction interval؛
- تصمیم اقتصادی.

این محدودیت عمدی است. اول باید ورودی معتبر و قابل توضیح داشته باشیم؛ بعد مدل و uncertainty را اضافه می‌کنیم.

## چطور خودت فاز ۱ را توضیح بدهی؟

می‌توانی این‌طور توضیح بدهی:

> در فاز اول یک قرارداد صریح برای داده تعریف کردم. سیستم قبل از هر مدل‌سازی بررسی می‌کند که فایل خالی نباشد، target و time column لازم وجود داشته باشند، ستون‌های گروهی گم نشده باشند و timestamp قابل تحلیل باشد. نتیجه به شکل CONTINUE، REWORK یا STOP تولید می‌شود و دلیل‌ها هم به‌صورت نام‌های machine-readable ذخیره می‌شوند. این فاز هنوز کیفیت مدل را تضمین نمی‌کند؛ فقط اجازه نمی‌دهد روی ورودی نامعتبر، نتیجهٔ ظاهراً علمی بسازیم.
